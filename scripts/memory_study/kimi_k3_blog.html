Roofline Analysis for Kimi K3

If you haven't read it yet, start with Edward Yang's excellent walkthrough of DeepSeek-V3, which works out from first principles how the model is sharded across 2,048 H800 GPUs.

This post tries the same exercise for Kimi K3, a 2.78T-parameter model. The setup: 512 GB200 GPUs with 192 GB of memory each, a global batch of 16M tokens per step, and two context lengths, 8K and 32K. First we find every parallelism config that fits the model on this cluster. Then we build a performance roofline to see which of them trains fastest.

1. Kimi K3 at a Glance

Kimi K3 is a 93-layer decoder. Two kinds of attention alternate through it:

  • KDA (Kimi Delta Attention), a linear-attention layer whose cost grows linearly with sequence length. 69 of the 93 layers use it.
  • MLA (Multi-head Latent Attention), DeepSeek's full attention with compressed keys and values, whose cost grows quadratically. Every fourth layer is MLA, 24 in all.

Every layer except the first is a mixture-of-experts (MoE) layer: 896 routed experts, of which each token picks 16, plus one shared expert that every token uses.

Attention residuals are new in Kimi K3. Instead of taking only the previous layer's output, each layer's input is a learned, softmax-weighted mix of many earlier layers' outputs. Keeping every layer's output around would be expensive, so the layers are grouped into blocks of 12 (the rows above). Inside a block, outputs add up into a running sum; when the block ends, that sum becomes a single entry on a stack. Each layer's input mixes the stack entries (the embedding and every finished block) with the current block's running sum. With 93 layers that is at most 9 sources instead of 93, which keeps memory down and, as we will see later, keeps the data passed between pipeline stages manageable.

1.1 Almost All of It Is Experts

Component Parameters Share
Routed experts 2,723B 98.0%
Attention 36B 1.3%
Shared experts 12B 0.4%
Everything else 8B 0.3%
Total 2,779B

Routed experts are 98% of the model: 92 layers x 896 experts of 33M parameters each. Yet each token only visits 16 of the 896, so a token touches about 105B parameters, under 4% of the model. That gap sets up everything that follows: memory has to hold all 2.78T parameters, but compute only pays for the 105B each token uses.

2. The Cluster and the Training Run

The intro gave the headline numbers; here are the details the rest of the post leans on.

2.1 The Cluster

  • 512 GB200 GPUs, each with 192 GB of HBM, 2.5 PFLOPS of dense bf16 compute and 5 PFLOPS in FP8.
  • The GPUs sit in 8 NVLink domains of 64. Inside a domain every GPU reaches every other at 900 GB/s per direction; between domains traffic goes over InfiniBand, which we assume runs at 50 GB/s per GPU per direction -- about 18x slower. Which parallelism lands on which link turns out to matter a lot (Section 6).

2.2 The Training Run

  • A global batch of 16M tokens per step: 2,048 sequences at 8K context, or 512 at 32K.
  • fp32 master weights, gradients and optimizer state (Muon), with bf16 compute.
  • Full activation rematerialization: each layer's forward is recomputed during backward, trading compute for memory.
  • Routed experts run on DistMoE, which fuses token dispatch, the grouped expert GEMMs and the combine into a few kernels.

3. What Fits in 192 GB

  • Persistent state alone (fp32 weights, gradients, optimizer) is about 33 TB: it has to be sharded over all 512 GPUs.
  • Activations: full remat keeps one input per layer; DistMoE adds its saved inputs, outputs and scratch.
  • Sharding options: FSDP + EP 64, PP 8 / 16 (ZeRO-1 or ZeRO-3), CP and TP to split each sequence.

4. The Compute Roofline

  • Every GPU processes 16M / 512 = 32K tokens per step, whatever the parallelism, so the FLOPs per GPU are fixed.
  • 8 FLOPs per parameter per token for the linears (forward, remat forward, dgrad, wgrad); routed experts the same with k = 16; MLA 4.5x its forward; KDA from a measured model.
  • One assumed efficiency for every matmul: 70% of peak in bf16, 60% in MXFP8.

5. Does the Roofline Hold?

5.1 Kernels

  • Dense GEMMs: 64-69% of peak at 2K+ rows; wgrad and small projections lower.
  • DistMoE GEMM kernels: 60-67% at 2K+ local tokens, 44-56% at 1K; helper kernels a roughly fixed ~2 ms per call. MXFP8 at most 43%.
  • MLA (FA4): 36-52% forward + backward.
  • KDA: costed from a measured model; under CP 1.3-2x slower than the same tokens without CP.

6. Communication

  • Topology: 8 NVLink domains of 64; InfiniBand between them.
  • Which link each parallelism uses: EP, CP, TP inside a domain; a PP stage sits in one domain, so FSDP within a stage is NVLink and PP hops are InfiniBand; without PP, FSDP spans all 512 GPUs and crosses InfiniBand.
  • Overlap rules: FSDP behind the neighbouring layer's compute, EP behind the expert GEMMs (fused in DistMoE), TP async behind its GEMMs, CP assumed hidden.

7. Step Time and Ranking

  • Step = compute + PP bubble + exposed communication (+ FSDP staging copies).
  • Two compute numbers: roofline (70% of peak) and calibrated (measured kernel efficiencies + work outside the roofline).
  • Without PP, FSDP over InfiniBand dominates (40+ s exposed at 8K).
  • With PP, FSDP and EP hide on NVLink; the cost moves to the bubble and the inter-stage hops.

8. How the PP Step Time Is Computed

  1. Split 93 layers into stages (12 per stage at PP 8).
  2. Time each stage for one microbatch.
  3. Time the hop after each stage: hidden state + AttnRes blocks so far.
  4. 1F1B: t_step = (M + P - 1) x (t_stage + 2 x t_hop).

Worked example: PP 8, ZeRO-1, TP 2 at 8K -- compute 17.8 s, hops 1.3 s, bubble 1.9 s, step 21.1 s (roofline).

Observations:

  • The last stage is underloaded (9 layers): idle about 25% of every slot.
  • The hops grow with depth because the AttnRes stack grows.
  • At 32K the bubble is large because M is small: M = P x cp x tp.

9. TP vs CP

  • At equal degree, the only real difference is KDA (and a little from dense GEMM rows).
  • Degree 2: TP slightly faster (no CP summary pass). Degree 4+: CP faster (KDA's TP speedup flattens).
  • Mixing pays both overheads.
  • TP's real advantage is memory: it shards the dense weights (127 GB vs 150 GB at 8K under ZeRO-1). Without PP it also halves FSDP's InfiniBand traffic.

10. What Changes the Answer

  • More memory (GB300, 288 GB): no-PP FSDP + EP 64 at 32K CP 1 x TP 1 becomes the fastest (25.8 s calibrated, 19.4 s roofline): one microbatch of 32K tokens hides FSDP even at roofline speed.
  • Rule of thumb: no-PP FSDP over InfiniBand works once a microbatch carries about 20-30K tokens per GPU.
  • Larger global batch: PP's bubble disappears, its hops and per-call penalty stay; PP wins on the roofline from 2x the batch, no-PP stays ahead with today's kernels.
  • Faster kernels expose no-PP's FSDP: improvement moves the answer toward PP.

11. Open Problems

  • Memory: fake-PG peaks 40%+ above the memory model.
  • KDA under CP: 0.7 s of the 2.4 s at 32K CP 2 unexplained (multi-document kernels?); CP 8 not measured.
  • MXFP8 DistMoE at most 43% of peak.
  • DistMoE faults instead of raising when an expert overflows its scratch.
  • Multi-node communication not measured; flat FSDP rings assumed.
  • Eager-mode idle (4-6 s per step) needs a CUDA-graph or compiled run.

Appendix A: Methodology

  • Kernel benchmarks: GB300 devserver (shared), CUDA-graph replays for GEMMs, minimum over repeats where other jobs interfered.
  • DistMoE: EP 4 over NVLink, Kimi K3's 14 / 28 local experts, balanced routing, 25% scratch headroom; GEMM kernel time separated from helper kernels.
  • Fake-process-group runs: one GPU stands in for rank 0 of 512; real kernels, collectives move no data; DistMoE stand-in (SwiGLU, 1,024 experts).
  • Communication: nccl-tests on 4 GPUs; InfiniBand assumed.
  • Configs and memory: the memory page (kimi_k3_params.html).
