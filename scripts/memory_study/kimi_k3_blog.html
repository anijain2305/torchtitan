Roofline Analysis for Kimi K3

If you haven't read it yet, start with Edward Yang's excellent walkthrough of DeepSeek-V3, which works out from first principles how the model is sharded across 2,048 H800 GPUs.

This post extends that exercise to Kimi K3. Kimi K3 brings constraints the DeepSeek-V3 analysis did not need to explore:

  • A 4x bigger model on fewer GPUs. 2.78T parameters (vs 671B) on 512 GB200s (vs 2,048 H800s), so memory is tight from the start.
  • Deeper, with longer context. 93 layers (vs 61) at up to 32K tokens: activations outgrow what FSDP and EP can fit, so we also investigate context and tensor parallelism.
  • Attention residuals. Each layer reads from many earlier layers, which complicates pipeline parallelism.
  • Built to actually run. The goal is to train this model in TorchTitan, so we trade paper idealizations for practical choices: DistMoE for the experts, more precise memory and latency models, and memory and compute checked against fake-process-group runs in PyTorch.

1. Kimi K3 at a Glance

Kimi K3 is a 93-layer decoder. Two kinds of attention alternate through it:

  • KDA (Kimi Delta Attention), a linear-attention layer whose cost grows linearly with sequence length. 69 of the 93 layers use it.
  • MLA (Multi-head Latent Attention), DeepSeek's full attention with compressed keys and values, whose cost grows quadratically. Every fourth layer is MLA, and so is the last one: 24 in all.

Every layer except the first is a mixture-of-experts (MoE) layer: 896 routed experts, of which each token picks 16, plus one shared expert that every token uses.

Attention residuals are new in Kimi K3. Instead of taking only the previous layer's output, each layer's input is a learned, softmax-weighted mix of many earlier layers' outputs. Keeping every layer's output around would be expensive, so the layers are grouped into blocks of 12 (the outlined rows above). Inside a block, outputs add up into a running sum, the partial; when the block ends, the partial becomes a single entry on a stack. Each layer's input mixes the stack entries (the embedding and every finished block) with the current partial, and one last mix over all of them feeds the LM head. With 93 layers that is at most 9 sources instead of 93, which keeps memory down and, as we will see later, keeps the data passed between pipeline stages manageable.

That gap sets up everything that follows: memory has to hold all 2.78T parameters, but compute only pays for the 105B each token uses.

2. The Cluster and the Training Run

The intro gave the headline numbers; here are the details the rest of the post leans on.

2.1 The Cluster

  • 512 GB200 GPUs, each with 192 GB of HBM, 2.5 PFLOPS of dense bf16 compute and 5 PFLOPS in FP8.
  • The GPUs sit in 8 NVL domains of 64 (64 of each NVL72 rack's 72 GPUs): an NVL domain is a group of GPUs connected to each other by NVLink. Inside an NVL domain every GPU reaches every other at 900 GB/s per direction, of which collectives over 64 GPUs reach about 640 GB/s. Between NVL domains traffic goes over InfiniBand: on this cluster each GPU has two 400 Gb/s NICs, 100 GB/s per direction, about 6x slower than NVLink collectives. Which parallelism lands on which link turns out to matter a lot (Section 6).

2.2 The Training Run

  • A global batch of 16M tokens per step: 2,048 sequences at 8K context, or 512 at 32K.
  • Mixed precision: master weights, gradients and optimizer state (Muon) stay in fp32; the dense linears (attention projections, shared experts) run their matmuls in bf16, and the routed experts in MXFP8, 8-bit operands with a shared scale per 32 elements, to use GB200's FP8 throughput. The Kimi K3 report also limits MXFP8 to the routed experts. In TorchTitan's config:
    • training.dtype = "float32": parameters and optimizer state are fp32.
    • training.mixed_precision_param = "bfloat16": FSDP all-gathers parameters in bf16.
    • training.mixed_precision_reduce = "float32": gradients are reduced in fp32.
    • DistMoE's expert_precision="mxfp8": quantizes the gathered routed expert weights to MXFP8 for the matmuls.
  • Routed experts run on DistMoE, which fuses token dispatch, the grouped expert GEMMs and the combine into a few kernels.

3. The Memory Problem

Kimi K3 has 2.78T parameters. Stored in fp32, the weights alone are 11.1 TB, 58 times one GPU's 192 GB. But weights are only part of what lives in GPU memory during training, and not the largest part. Let's look at what else is there.

3.1 Persistent State

Training needs room for three things per parameter for the whole run: the fp32 master weight, its fp32 gradient, and the optimizer state (Muon keeps one fp32 momentum buffer). That is 12 bytes per parameter:

Bytes per parameter Kimi K3
Master weights (fp32) 4 11.1 TB
Gradients (fp32) 4 11.1 TB
Optimizer state (Muon, fp32) 4 11.1 TB
Total 12 33.4 TB

33.4 TB is 174 times one GPU's 192 GB, before a single activation is stored.

We ignore the AdamW optimizer state, since the parameters it covers are only 0.09% of the model.

This is a deliberately simple mental model: no parallelism yet, and none of its implementation details. Once FSDP comes in, for example, each GPU also keeps temporary bf16 copies of the weights it gathers for compute. We add those details as each parallelism is introduced later.

3.2 Stashed Activations

The forward pass keeps some tensors around for the backward pass. We call them stashed activations, to avoid the word "saved", which is easily confused with saving memory. Unlike the persistent state, they scale with tokens, not parameters.

To keep things simple, a microbatch is one sequence: 8,192 tokens at 8K, or 32,768 at 32K. Measured with a fake-tensor run (see Appendix B.1 for how), one sequence stashes 746 GB at 8K and 3.0 TB at 32K (4x the footprint at 8K). The toggle at the top right switches the charts between the two.

This is deliberately simple again. Tensor parallelism (with sequence parallelism) and context parallelism split each sequence across GPUs and shrink what each one stashes; we bring them in when we get there.

The attention residuals run on TorchTitan's fused Triton kernel (an opt-in override adapted from Flash Linear Attention). It reads the block stack and the current partial sum directly, so it stashes no concatenated copies of them.

3.3 Rematerialization

Rematerialization (torch_remat, commonly known as activation checkpointing) stashes fewer tensors in the forward pass, and recomputes them during backward. With full remat, each layer keeps only its input (plus the routing decisions), and the activations of one 8K sequence drop from 746 GB to 15.6 GB, about 48x less. The price is one extra forward pass: 8 FLOPs per parameter per token instead of 6, about 33% more compute.

Recompute's contribution to the peak. Before each layer's backward, remat reruns its forward, recreating that layer's intermediate activations: about 6 GB per 8K tokens, one layer at a time. The peak comes at the first layer of the backward pass, when the whole stash is still live, so it is the stash plus one layer's working set.

The chart below compares no remat, TorchTitan's default remat (which keeps every region the model declares except the routed experts' first projection, w13, recomputing only that) and full remat, drawn as its stash plus the recompute peak. From here on, full remat means both: 21 GB per 8K sequence.

3.4 DistMoE

DistMoE is a recent library from the PyTorch team for running MoE layers efficiently: its kernels overlap the token dispatch and combine with the expert GEMMs, drop no tokens, and work with CUDA graphs. Any production training system has something like it to efficiently manage routing imbalance, and its implementation changes both memory and speed. So even though it pulls us away from the idealized picture, we bring it in now.

Memory is tight, so we configure DistMoE to recompute too: per MoE layer it stashes only the layer's input and recomputes the expert intermediates in backward. On top of full remat, that adds four things:

  • Its stashed input, held in DistMoE's own preallocated buffer.
  • Its output, which full remat keeps instead of recomputing (why: see Appendix B.2).
  • Scratch for one layer's temporaries, reused by every layer and sized with a capacity factor of 4 so that experts receiving more than their share of tokens still fit.
  • Routing indices: three int64 index arrays per MoE layer, stashed so the backward can send gradients back to the right tokens. They are negligible without expert parallelism (0.3 GB at 8K), but they are sized for the worst case across the expert-parallel group, so with EP 64 they grow 56x, to 16 GB (Section 4).

3.5 MXFP8

MXFP8 runs the matmuls on 8-bit operands with a shared scale per 32 elements, about 1 byte per element instead of 2. We use it for the routed experts only, through DistMoE's own MXFP8 kernels; the dense linears stay in bf16. Memory barely changes: with full remat, a layer stashes only its bf16 input, so there is little left for MXFP8 to shrink. DistMoE still stashes its input in bf16, and its scratch shrinks by only about 6% (23.6 to 22.2 GB at 8K), since most of its temporaries stay in bf16. The rest of the post keeps the bf16 figure, 23.6 GB, a slightly conservative bound.

3.6 Where We Stand

Rematerialization brought the activations down to 56 GB per 8K sequence, well under one GPU. At 32K the problem is not solved: 223 GB is still more than a whole GPU, before anything else is stored. We come back to it with context and tensor parallelism (Section 4.3, Section 4.4). The persistent state has not moved: 33.4 TB, 174 times one GPU. No single-GPU trick fixes that; it has to be split across many GPUs.

4. Using Parallelism to Fit the Model

Let's now spread the model across the cluster. The goal of this section is to find the parallelism configs that fit Kimi K3 in memory; how fast each one trains (its step time) comes later. Along the way we build an intuition for how the different kinds of parallelism interact: what each one shards, what it leaves untouched, and what it costs in extra memory. We also bring in the implementation details of PyTorch's sharding techniques that affect memory, so the numbers get closer to what a real run would use.

4.1 ZeRO / FSDP

We start with plain data parallelism over all 512 GPUs. 2,048 sequences per step (at 8K) gives each GPU 4 sequences, run one at a time as 4 microbatches with gradient accumulation. Every GPU runs the whole model, so on its own data parallelism only multiplies the problem; ZeRO is what shards the persistent state across those 512 copies, in three stages:

  • ZeRO-1 shards the master weights and optimizer state: each GPU keeps 1/512 of them, 22.2 TB down to 49.5 GB (including some padding, below).
  • ZeRO-2 also shards the gradients: 11.1 TB down to 24.8 GB.
  • ZeRO-3 also shards the weights used for compute. This is what PyTorch's FSDP does by default without pipeline parallelism, so we use "ZeRO-3" and "FSDP" interchangeably.

Compute weights. Sharding the master weights has a catch. A GPU holding 1/512 of the fp32 master weights cannot run a forward pass on them, so it needs a separate copy of the weights in the format the matmuls use: the compute weights: MXFP8 for the routed experts, about 1 byte per parameter, and bf16 for everything else. (FSDP gathers the experts in bf16 and frees that buffer once their MXFP8 copy is built; the fake runs in Section 4.8 agree.) Under ZeRO-1 and ZeRO-2 every GPU holds the whole model's compute weights: 2.84 TB, which after ZeRO-2 is the largest thing left.

The ZeRO-1 and ZeRO-2 rows are straightforward: the master weights and optimizer state (ZeRO-1), then the gradients (ZeRO-2), drop to their 1/512 shards, but every GPU now has to hold the whole model's compute weights.

The ZeRO-3 row. ZeRO-3 shards the compute weights too: FSDP gathers a layer's weights just before it runs and frees them afterwards. Yet the gradients column jumps, which is counterintuitive: ZeRO-3 only adds sharding of the compute weights, so the gradients should stay where they were. The reason is a second catch. To hide the communication, FSDP works one layer ahead: while one layer computes, the next layer's weights are already being gathered, and in backward the previous layer's full gradient is still being reduce-scattered. So at the peak, in backward, a GPU holds two layers' compute weights and two layers' full gradients on top of its shards, plus remat's recompute working set for one layer (Section 3.3). Because the model is so large, two layers' worth of gradients is 242 GB on its own.

Padding. FSDP splits each tensor along its first dimension, and pads it when that does not divide evenly. For the expert weights that dimension is the expert count, 896 over 512 GPUs, which pads to 1,024: 14% more for the expert part of every shard.

4.2 Expert Parallelism

Under ZeRO-3, holding two unsharded layers is a lot: 242 GB of gradients and 61.8 GB of compute weights, more than a whole GPU on their own, and almost all of it is experts. We need a way to shard what a GPU gathers, not just what it stores. Enter expert parallelism (EP).

EP is counterintuitive at first. With EP 64, the 896 experts of every layer split into 64 groups of 14, and each group lives on 8 GPUs: FSDP shards the group's 14 experts over those 8 along the expert dimension, so each GPU stores two whole experts (14 pads to 16; the eighth GPU stores none). So each GPU still stores about 1/512 of the weights, as before. The difference is in what it gathers. Without EP, the two layers in flight hold the unsharded gradients and compute weights of all 896 experts; with EP, only those of the GPU's group of 14. The expert part of those per-layer buffers shrinks 64x, taking the in-flight gradients from 242 GB to 8.8 GB and the compute weights from 61.8 GB to 3.5 GB (the dense part of each layer, in bf16, does not shrink). The padding stays: each group's 14 experts are sharded over 8 GPUs, which pads to 16.

Caveat: DistMoE's routing indices. For backward, DistMoE stashes three int64 index arrays per MoE layer, sized for the worst case: EP x tokens x 14 entries. With EP 64 at 8K that is 16.2 GB over 92 layers, which is why the EP row's activations jump from 56 to 72 GB in Section 4.1's table. (We are working with the DistMoE authors to shrink this.)

Insight

Sharding what a GPU stores does not shard what it holds at the peak. FSDP stores 1/512 of everything, yet the layers in flight are unsharded: two layers' compute weights and gradients, hundreds of GB for a large MoE layer. EP does not change what each GPU stores; it shrinks what each GPU gathers, from every expert of a layer to its own.

Finally, with FSDP over 512 GPUs plus EP 64, the model fits at 8K: 158 GB per GPU. At 32K the activations are 223 GB even before DistMoE's routing indices, which grow to 65 GB with EP 64, so it is far from fitting. Spoiler: we will need context or tensor parallelism.

4.3 Context Parallelism

Context parallelism (CP) splits each sequence across GPUs: with CP 2, each GPU holds half of a sequence's tokens. Everything that works token by token -- the projections, the norms, the MoE layers -- runs on the local tokens with no extra communication. Only attention needs the other GPUs' tokens: MLA uses Ulysses, and KDA, being a recurrence, passes a small summary of each chunk's state along. What that costs in time comes later; here we only care about memory.

For memory, CP is exactly the lever the previous step was missing. Activations scale with tokens per GPU, so CP divides them, DistMoE's stash, output and scratch included. Nothing else changes. The CP ranks join the FSDP group, so each GPU still stores 1/512 of the persistent state, and the layers in flight are the same weights and gradients whatever the token count. The work per GPU does not change either: each GPU now runs CP times as many microbatches, each 1/CP of a sequence. 4.5 Pipeline Parallelism

So far every parallelism has been SPMD: every GPU runs the same program on its own slice of the data, weights or tokens. FSDP and EP, with CP 4 or TP 4 at 32K, already fit the model this way. So why look further? Because memory is not the only thing that matters:

  1. Without PP, FSDP gathers and reduce-scatters every layer for every microbatch, across all 512 GPUs. CP and TP multiply the microbatches, and with them that traffic and the weight copies and re-quantization that come with each gather.
  2. Those all-gathers and reduce-scatters run on the GPU's SMs and slow down the compute they overlap with.

We model both later. For now, take them as a reason to look, and see how the model shards with PP.

Pipeline parallelism (PP) cuts the model into stages of consecutive layers and gives each stage its own group of GPUs. With PP 8, for example, there are eight stages of about 12 layers (93 does not divide evenly), each on 64 GPUs (one NVL domain). Inside a stage we use FSDP and EP as before, over the stage's GPUs, so EP stays 64 (it drops to 32 with PP 16, which the table below also shows).

What PP does to memory:

  • Each GPU only stores its stage. But 1/P of the layers, sharded over 512/P GPUs, is still about 1/512 of the model: same memory as before.
  • Microbatches pile up on the first stage. With the 1F1B schedule, the first stage holds P microbatches in flight, each stashing activations for its 93/P layers. P microbatches x 93/P layers is about one whole-model microbatch: same memory as before. This depends on the schedule, though: interleaving, in the next section, keeps more in flight.
  • ZeRO-1 becomes affordable. Without PP, ZeRO-1 meant every GPU holding the whole model's compute weights and gradients, 14 TB. With PP it only has to hold one stage's, and that fits. This is FSDP's default under PP: a stage's compute weights stay gathered and its gradients unsharded for the whole step, instead of being regathered and reduce-scattered for every microbatch. That is where the performance win can come from, at the cost of some memory.
Insight

A ZeRO stage is really a choice of how much stays unsharded. PP shrinks that from the whole model to one stage, which turns ZeRO-1 from impossible (14 TB per GPU) into affordable, and with it, keeping weights gathered and gradients unsharded across microbatches instead of paying FSDP's communication on every one.

4.6 Interleaved Pipeline Parallelism

Interleaved 1F1B gives each rank v smaller stages (virtual stages) instead of one: with PP 8 and v = 2, rank 0 runs layers 0-5 and 48-53, rank 1 layers 6-11 and 54-59, and so on, so each microbatch loops through the ranks v times. What it buys is a smaller pipeline bubble, by a factor of v, which we come back to with the step time. What it costs is memory:

  • Each GPU stores the same weights. A rank still holds 1/P of the layers, only in v pieces: the shards, compute weights and gradients do not change.
  • More microbatches pile up on the first rank. Before its first backward, rank 0 runs (v - 1) x P + 2 x (P - 1) forward chunks (PyTorch's ScheduleInterleaved1F1B), so it holds about (v + 1) P chunk-microbatches in flight instead of P. Each chunk has only 93 / (P v) layers, so in layers that is about (v + 1) / v times 1F1B's: 1.5x at v = 2, 1.25x at v = 4. Everything stashed per layer and microbatch grows with it: the activations, DistMoE's routing indices, and its stashed inputs and outputs.

4.8 How Close Are We to a Real Run?

Every number so far comes from the model. Checking it on 512 GPUs would be expensive, but PyTorch has a neat trick: a fake process group. One process plays a single rank of the 512-GPU job. For PP, a hybrid mode runs one real process per stage, with real send/recv between them, and fakes everything else. TorchTitan exposes both modes (--comm-backend fake and real_pp_fake_spmd).

5. The Compute Roofline

Memory told us which parallelism configs fit. Now we want to know how fast each one trains. We start with compute alone: how long one step takes with no communication and nothing else in the way.

We build that estimate in two passes:

  • The ideal roofline (Section 5.1) runs every op at a fixed fraction of the GPU's peak: one assumed efficiency for all GEMMs, full HBM bandwidth for everything else. It is quick to compute and good for finding compute bottlenecks.
  • The practical roofline (Section 5.2) assumes the compute kernels are already well optimized (we do not plan to improve cuBLAS's matmuls in this study) and times each one at the shapes each config produces. It needs profiling on the hardware we care about, but it is more accurate, which makes it the right model for ranking configs. It is not a tool for finding compute bottlenecks: it takes every kernel's measured speed as given. This is the model the rest of the post builds on.

5.1 The Ideal Roofline

Every GPU processes the same number of tokens per step, whatever the parallelism: 16M tokens / 512 GPUs = 32,768 tokens. With full remat, a linear layer costs 8 FLOPs per parameter per token: 2 in forward, 2 when remat reruns it, and 4 in backward.

5.2 A Practical Roofline

Most roofline studies stop at something like the ideal roofline. It is a first-order model, built to show where the bottlenecks are, and it can be far off: for FSDP 512 + EP 64 at 8K it predicts 15.6 s, while the same step, run with a fake process group (real kernels, collectives that move no data), measures 20.6 s of GPU time (Section 5.2.5). We want more than bottlenecks: we want to use this model to choose how to run Kimi K3 on our cluster, so it has to be more accurate.

For that, we can lean on what we know about our framework. Like many practitioners, we know which parts are already well optimized: in this study, the compute kernels. So instead of one assumed efficiency for every GEMM, we run each matmul at the shapes the parallelism configs actually produce and measure its efficiency. The model still leaves out communication and pipeline bubbles, which come later.

Insight

A roofline model is not one-size-fits-all. What you know about your framework and what you need the model for decide how to build it: a first-order model to find bottlenecks, or measured kernels at your exact shapes to choose between configs.

All measurements run on one GB300, which has the same bf16 (2.5 PFLOPS) and FP8 (5 PFLOPS) peaks as GB200, so the percentages carry over. Kernels are timed as CUDA-graph replays: kernel time, no CPU launch overhead.

5.2.1 Compute Ops at Each Config's Shapes

The compute kernels are well optimized, so the model uses the efficiency they actually reach at each config's shapes. Parallelism changes those shapes. For a linear's forward GEMM (M x K) @ (K x N), M is the tokens (rows), K the input width and N the output width:

  • CP: fewer tokens per microbatch, so smaller M.
  • TP: narrower dense weights at the same M (a few small ones stay whole): smaller N for column-parallel linears, smaller K for row-parallel ones. The MoE runs on TP-local tokens, so like CP it gives each expert a smaller M.
  • EP: experts per GPU (14 at EP 64, 28 at EP 32); with the local tokens, that sets each expert's M.
  • PP: no shape of its own; PP 16 means EP 32.

In the weight-gradient GEMM the tokens are the reduction dimension, so there CP shrinks K instead.

5.2.3 The Optimizer Step

Every step ends with the optimizer: DistMuon, Muon over the sharded parameters. Muon orthogonalizes each weight matrix with a few Newton-Schulz iterations, so it needs whole matrices, and how much it has to move depends on how they are sharded:

  • Routed experts, 98% of the parameters: nothing to move. FSDP shards each group's 14 experts along the expert dimension, so a GPU's shard of the gradient, momentum and weights is two whole experts, and it orthogonalizes them where they are.
  • Dense weights: a small redistribution. They are sharded by rows, so DistMuon gathers each matrix (or each head's block) to one GPU, runs Newton-Schulz there and sends the update back: about 0.2 GB each way per GPU per step, a few milliseconds.

So the optimizer is almost all compute, and about the same per GPU in every config: each GPU holds about 1/512 of the parameters either way. Measured in fake-process-group steps at 8K:

Caveat

Today FSDP 512's optimizer step takes 3.1 s, because DistMuon runs eagerly: for all 93 layers' parameters it launches about 700,000 small kernels, and the GPU waits on the CPU that launches them. A PP rank holds a quarter of the layers or fewer, so the CPU keeps up. The step cannot be captured in a CUDA graph yet (among other things, its learning rate is a Python number, baked into a capture); once it can, FSDP 512 gets those 2.3 s back. Side note

Why build the practical roofline at all, if a fake-process-group run measures the step directly? Because the step is not one number once communication enters. Each collective overlaps a different part of the compute: FSDP's gathers the next layer's GEMMs, DistMoE's dispatch the expert GEMMs, and TP's and CP's sit between the ops that wait for them. To tell whether a collective is really hidden, and which compute it slows down, we need the time of each op, not one total.

From here on, "the roofline" means this practical roofline, not the ideal one from Section 5.1.

6.1 Overlap Is Not Free

But in reality, "hides behind" does not mean free. An NCCL collective is a kernel: each of its channels is one thread block pinned to one SM, and every byte it moves is read from HBM on one GPU and written on another. So the overlapped compute gets fewer SMs and less memory bandwidth, and the collective itself slows down too. For SPMD collectives, every rank runs the kernel, so every GPU pays.

We measured it on 16 GPUs connected by NVLink, as the GPUs of one 64-GPU NVL domain are (Appendix B.5): each collective running back to back on a side stream while a GEMM, or a memory-bound kernel, runs on the main stream:

6.2 Crossing NVL Domains

Only two kinds of traffic leave a 64-GPU NVL domain: FSDP's all-gathers and reduce-scatters without PP, which span all 512 GPUs, and PP's hops between stages, which sit in different NVL domains. Both go over InfiniBand. Each GPU of our cluster has two 400 Gb/s NICs, 100 GB/s per direction together, about 6x slower than NVLink collectives (about 640 GB/s); below, "a GPU's NIC" means both.

One rule covers both. FSDP gathers each weight from, and reduce-scatters its gradient over, the GPUs that shard it: its FSDP group. NCCL runs these collectives as a ring through every GPU of the FSDP group: over NVLink inside an NVL domain, through NICs between NVL domains. An FSDP group with k GPUs in each NVL domain has k NICs there, and NCCL spreads the ring's traffic over all of them, so:

Bandwidth=min(NVLink, k × one NIC)k: number of GPUs of the FSDP group in each NVL domain

7. Pipelines: Hops and Schedules

With compute (Section 5) and communication (Section 6) modelled, one piece of the step time is left: the pipeline itself. A PP step is more than each stage's work: microbatches move between stages in hops, and stages wait on each other. This section builds the step time of a PP config from two choices: the pipeline schedule (plain or interleaved 1F1B), and how a hop carries Kimi K3's attention residuals (the transport).

7.1 Schedules

Every pipeline schedule trades peak memory, bubble and step time differently, and each would need its own model. We keep to two, both in TorchTitan:

  • Plain 1F1B alternates one forward and one backward per stage, so a stage never holds more than P microbatches at a time: that bounds its activation memory.
  • Interleaved 1F1B splits each stage into v chunks to shrink the pipeline bubble, at the cost of holding more microbatches at a time.

A pipeline's bubble is the time a stage sits idle. It comes from three places: the warmup, while the first microbatches travel down the pipeline and the later stages wait for work; the cooldown, while the last ones drain and the early stages have nothing left; and the hops in between, when a stage has to wait for its input to arrive from another one. We build up the step time piece by piece, with P equal stages, M microbatches (not the GEMM rows M of Section 5), t one stage's forward and backward for one microbatch, and h one hop. (In the real pipeline both change from stage to stage: the stages are uneven, and a hop's bytes depend on the transport (Section 7.2) and where it sits in the pipeline. Our model represents that: for every config it simulates the schedule itself, each chunk's forward and backward with its compute, communication and penalties, each hop with its own bytes. Equal stages and hops here just keep the explanation simple.)

Warmup and cooldown. Each stage has M t of work. But the last stage cannot start until the first microbatch has gone through the P - 1 stages before it, and the first stage cannot finish until the last microbatch's backward has come back through them. Every stage idles (P - 1) t in total, split differently: the last stage waits (P - 1) forwards at the start and (P - 1) backwards at the end, while the first stage does all its waiting at the start, until the first backward comes back. Interleaving splits each stage into v chunks of t / v, so the pipeline fills and drains in chunk-sized steps: (P - 1) t / v.

Hops in plain 1F1B. Every microbatch's round trip, down the pipeline and back, crosses 2 (P - 1) hops. Plain 1F1B lets each stage hold only as many microbatches as keep it busy while that trip runs, if the trip were compute only. So the stages end up waiting for every hop: 2 (P - 1) per microbatch, shared by the P stages that work in parallel, or 2 (P - 1) / P hops per microbatch, almost two, for the whole step (plus 2 (P - 2) more while the pipeline fills and drains).

7.2 What a Hop Carries

Besides the hidden state, a stage needs the attention-residual blocks that earlier stages finished (Section 1). How they get there is the hop's transport. TorchTitan uses one for each schedule:

  • chain (plain 1F1B): every hop carries the hidden state and the whole block stack so far, so the hops grow along the pipeline: at PP 8 the hop into the last stage carries nearly three times the bytes of the hop into the second. The backward mirrors it, with the blocks' gradients.
  • cache (interleaved 1F1B): a rank comes back for later chunks of the same microbatch, so it keeps the blocks it received for its earlier chunks, and a hop carries only the hidden state and the blocks the receiving rank has not seen yet.

Above each forward hop: what it carries; h is the hidden state, colored squares are attention-residual blocks (E: the embedding). The backward mirrors each, with gradients.

The transport sets the hop time h of Section 7.1: chain's grows along the pipeline, cache's stays small after the first lap. Section 8.4 asks whether a transport TorchTitan does not have would do better.

8.1 Why FSDP 512 Without PP Falls Behind

At 8K, even the best FSDP 512 config is well behind the leader, and the others fare much worse. Why?

  • Overlap is not free. FSDP's collectives almost hide behind each layer's compute, but hiding them means running alongside nearly all of it, and slowing it down the whole time. On top comes the weight prep (copying the gathered weights, quantizing the experts), which FSDP repeats every microbatch and PP's ZeRO-1 does once per step.
  • CP and TP make it much worse. They multiply the microbatches, and that exposes the communication from both sides: each microbatch has fewer tokens, so less compute to hide behind, and there are more of them, so more all-gathers and reduce-scatters. At CP 4, a layer's forward takes about a third of the time its all-gather does.
  • TP is less bad than CP. Both sit at the bottom of the ranking, but TP also splits the dense weights, so FSDP has less to gather.

At 32K, FSDP 512 fares much better, which may be surprising at first. Memory forces every config into CP 4 or TP 4, and that treats the two families very differently. FSDP 512 gets the same 4 microbatches of 8,192 tokens per GPU as 8K without a split, so its FSDP cost does not grow, while longer attention gives it more compute to hide behind. PP, on the other hand, now pays for the split: exposed TP or CP, and a bigger bubble. So the gap closes to about a second.

8.2 Why PP 8 Wins Over PP 16

With FSDP 512 out of the running at 8K, the next questions build up, one at a time, why the leader is the fastest. First: PP 8 or PP 16? At the same split and schedule, PP 16 is slower every time, by about a second, and by more with deep interleaving. Why?

When we raise the PP degree, we usually think of the stages getting smaller. But it also shrinks everything inside a stage: with 512 GPUs, PP 16 leaves 32 GPUs per stage instead of 64, so the stage's SPMD mesh, and with it EP, halves (EP 32 instead of EP 64). That is the main reason PP 16 is slower here:

  • Smaller expert GEMMs. With EP 32 each GPU holds twice the experts (28 instead of 14) but processes the same tokens, so each expert gets half the rows, and the expert kernels run less efficiently. Together with the LM head, which weighs more on a 6-layer stage than on a 12-layer one, this slows the slowest rank by about a second: most of the gap in the top configs.
  • Twice the hops. A microbatch crosses twice as many stage boundaries, and with half as many data-parallel replicas each pipeline runs twice the microbatches.
  • Uneven chunks at v = 4. 93 layers over 64 virtual stages leaves chunks of one or two layers, and the imbalance stalls the schedule: at v = 4 this, not the experts, is the bigger cost.
Insight

Raising the PP degree shrinks everything inside a stage too. With a fixed number of GPUs, more stages mean fewer GPUs per stage, so smaller EP and smaller expert GEMMs.

At 32K, though, PP 16 ties the leaders. The reason is memory, the one thing PP 16 has going for it: each stage holds half the layers. At 32K every config needs a 4-way split, and the two splits are not equally cheap. CP 4 exposes little communication, since only attention communicates, while TP 4 exposes its collectives around every dense layer. PP 8 does not fit with CP 4, so it has to take TP 4 and pay for it; PP 16, with half the layers per stage, fits CP 4. The cheaper split makes up for PP 16's smaller expert GEMMs and bigger bubble. With TP 4, PP 16 loses to PP 8 as usual.

8.4 Do Attention Residuals Hurt PP?

The problem. Attention residuals give PP an unusual property: a stage needs the blocks of every stage before it, so with chain each hop carries a bigger stack than the last, and the latest stages, already the slowest (the last also runs the LM head), trade the most bytes, on the critical path (Section 7.2). A natural fix is direct, which TorchTitan does not have: each rank sends every block it finishes straight to the later stages that use it, asynchronously, so a hop carries only the hidden state, and the block traffic spreads over all pairs of ranks, off the critical path, while the stages compute.

8.6 How Far to Trust the Ranking

We have now worked out, from first principles, which configs to run and why. But there is a catch: this is a model, and the leaders sit within a few percent of each other. Small changes to the model can flip their order:

  • What it assumes: NVLink bandwidth and overlap inside a 64-GPU NVL domain (measured up to 32 GPUs), TP and CP fully exposed, a hop moving as soon as both sides are ready, and the optimizer at its GPU time.
  • What it leaves out: profiles of a real 512-GPU run show DistMoE slower than in our fake-process-group steps (about 1.65x the bare grouped GEMM instead of about 1.25x, plus waits at its barriers), and FSDP's dense collectives across all 512 GPUs slower than modelled. The first adds about the same to every config; the second only makes FSDP 512 slower still.

So the practical way to use the ranking is to take a few of the top configs and run them on the cluster. What the model gives the practitioner is a clear picture of what to expect and why: absolute times will be off, and the order of near-ties may change, but the big picture should hold. PP beats FSDP 512 at 8K, interleaving (at least v = 2) beats plain 1F1B, PP 8 beats PP 16 unless memory forces the split, and the transport hardly matters. If a run disagrees with that, it points to an inaccuracy in the model.

9. Open Problems

Two directions we have not explored, both of which could move the numbers:

  • The ideal roofline of DistMuon. The optimizer step is almost all Newton-Schulz iterations (Section 5.2.3), and each iteration multiplies a matrix by its own transpose. That product is symmetric, so a dedicated kernel needs to compute only half of it. We take DistMuon's kernels as they run today; a roofline built from the work Newton-Schulz really needs would show how much a faster optimizer could save.
  • Other pipeline schedules. We modelled plain and interleaved 1F1B. Splitting each backward into its input-gradient and weight-gradient halves lets a schedule fill the bubble with weight-gradient work: zero-bubble schedules, and V-shaped ones (each rank holding a chunk near each end of the pipeline) that balance memory across ranks. Each offers a different trade between bubble and memory, and with attention residuals, a different pattern of what each hop carries (Section 7).

Appendix A: Insights

  1. Sharding what a GPU stores does not shard what it holds at the peak. FSDP stores 1/512 of everything, yet the layers in flight are unsharded: two layers' compute weights and gradients, hundreds of GB for a large MoE layer. EP does not change what each GPU stores; it shrinks what each GPU gathers, from every expert of a layer to its own. (Section 4)
  2. For memory alone, when activations are what overflow, reach for CP or TP before pipeline parallelism. Both split the tokens of a sequence, and activations are the only part of GPU memory that grows with them, so they cut exactly the part that is too big. The sharding of weights, gradients and optimizer state stays as it was. For speed it is another matter: without PP, CP and TP are the slowest configs of all (Section 8.1). (Section 4)
  3. A ZeRO stage is really a choice of how much stays unsharded. PP shrinks that from the whole model to one stage, which turns ZeRO-1 from impossible (14 TB per GPU) into affordable, and with it, keeping weights gathered and gradients unsharded across microbatches instead of paying FSDP's communication on every one. (Section 4)
  4. Once EP shrinks the routed experts on each GPU, and ZeRO-1 (common with PP) keeps the stage's weights and gradients unsharded all step, the dense weights become a large share of what each GPU holds, and only TP splits them. Under FSDP alone, only two layers are ever gathered, so TP gains little over CP for memory. Details in Appendix B.3. (Section 4)
  5. A roofline model is not one-size-fits-all. What you know about your framework and what you need the model for decide how to build it: a first-order model to find bottlenecks, or measured kernels at your exact shapes to choose between configs. (Section 5)
  6. Hiding a collective is not free. While it overlaps compute, both run slower, so a model that only checks whether communication fits behind compute calls configs free that are not. (Section 6)
  7. Across NVL domains, bandwidth is set by how many NICs carry the traffic, not by how much data there is: k GPUs of a group in each NVL domain give it k NICs there. Placement that leaves a group one GPU per domain puts its whole ring on a single NIC. (Section 6)
  8. Raising the PP degree shrinks everything inside a stage too. With a fixed number of GPUs, more stages mean fewer GPUs per stage, so smaller EP and smaller expert GEMMs. (Section 8)
  9. Interleaving shrinks the bubble by about v and its extra work in flight hides the hops, at the price of memory; but once chunks shrink to a layer or two, the imbalance between them brings the bubble back. (Section 8)

B.1 Measuring Stashed Activations

kimi_k3_activations.py builds the full model under FakeTensorMode in bf16 (FSDP's compute dtype), so no memory is allocated, and runs one forward pass plus the cross-entropy loss inside a saved-tensors pack hook. The hook records every tensor autograd stashes for backward. Tensors are deduplicated by storage: a storage stashed by several ops, or through several views, is counted once at its full size. Parameters are excluded. The model's local_compile regions run as in training, so the compiler's partitioner decides what those regions stash.

The attention residuals run on TorchTitan's fused Triton override, a custom op with a fake implementation, so the same accounting covers it. It reads the block stack and the partial sum directly and saves only small per-token statistics, where the compiled region would stash a concatenated [T, N+1, D] copy of its inputs for every call.

B.2 Why Full Remat Keeps DistMoE's Output

Full remat stashes each layer's input in the forward pass. In the backward pass it first replays the layer's forward from that input, rebuilding the intermediates the gradients need (norm outputs, attention internals, residual sums), and then runs the backward.

TorchTitan excludes the DistMoE call from that replay: it is wrapped in remat.region(..., recompute=False) and its output is marked with remat.recompute_needs_tensor (torchtitan/models/common/dist_moe/routed_experts.py). When the replay reaches the MoE, it reuses the output from the original forward and carries on through the rest of the layer. So autograd keeps that output: a [tokens, 3584] bf16 tensor, about 59 MB per MoE layer at 8K, 5.4 GB over 92 layers.

The reason is that DistMoE already recomputes its own insides. It stashes only its input, and its backward re-dispatches the tokens and reruns the expert forward GEMMs to rebuild the intermediates it needs. Replaying the call under remat as well would do that work twice in every MoE layer:

  • an extra dispatch and combine, the expert-parallel all-to-all (about 940 MB per GPU per transfer at 8K), and
  • an extra expert forward: 10 FLOPs per parameter per token for the routed experts instead of 8, about 25% more expert compute, on the quarter of the step that is experts.

Keeping the output trades 5.4 GB at 8K for avoiding both.

DistMoE's stashed input is a separate 5.4 GB, not the input full remat already keeps: the MoE input arrives mid-layer, after attention, the attention-residual mix, the norm and the down-projection into the 3,584-wide latent.

B.4 Counting the Memory-bound Bytes

The memory-bound terms of Section 5, per GPU per step. With full remat, forward ops run twice (forward and remat), and backward moves about twice a forward's bytes.

  • Attention residuals (TorchTitan's fused Triton kernel). Each layer mixes its sources twice (before attention and before the MoE). Over n sources of width D, forward and remat each read the bf16 sources once and write the output; backward reads them again with the output gradient and writes their gradients: about (8n + 6) x D bytes per mix in total. n grows from 1 to 9 across the 8 blocks, and each block's first layer also concatenates the stack.
  • MXFP8 quantization of the routed experts' weights (read bf16, write 8 bits plus one scale per 32 elements, about 3 bytes per element): three times per microbatch without PP (forward, remat, input gradient), but once per step in both orientations under PP's ZeRO-1, where the gathered stage stays alive. DistMoE quantizes the expert activations inside its fused kernels, so their cost is part of its measured time; the dense linears run in bf16 and need no quantization.
  • FSDP buffer copies. Each all-gather copies the bf16 weights out of the gathered buffer (read and write 2 bytes per parameter); each reduce-scatter copies the bf16 gradients into an fp32 buffer (2 + 4 bytes). Without PP: two gathers and one reduce-scatter per layer and microbatch. Under PP's ZeRO-1: once per step.
  • Norms (RMSNorm, KDA's L2 and gated norms, MLA's q / kv norms): 4 bytes per element forward and 6 backward, 14 over forward, remat and backward.
  • Everything else: the two residual adds, the output gates and the shared expert's SwiGLU. This bucket also holds casts and gradient accumulation we do not count, so it is the least accurate.

B.5 Communication Experiments

Hardware. Within one host: a 4-GPU GB300 machine (152 SMs per GPU, NVLink between the GPUs). Across hosts: a GB300 NVL72 cluster with 4 GPUs per host and one 800 Gb/s XDR InfiniBand NIC per GPU.

  • NVLink across hosts: the job asks the scheduler to place all its hosts in one NVL72 domain. Every GPU reported the same NVLink fabric and clique, and NCCL's log showed one node of 16 (or 32) ranks with every connection between hosts over NVLink (P2P/MNNVL). Enabling NVLink SHARP (NCCL_NVLS_ENABLE=1) did not change the bandwidth.
  • InfiniBand across hosts: NCCL's multi-host NVLink mode is turned off (NCCL_MNNVL_ENABLE=0), so each host's 4 GPUs talk over NVLink and traffic between hosts goes over the NICs: NVL domains of 4 GPUs joined by InfiniBand, at 8, 16 and 32 GPUs (2, 4 and 8 hosts). For NVL domains of 8, 4 hosts in one NVL72 domain are split into two NVLink cliques of 2 hosts (NCCL_MNNVL_CLIQUE_ID), so NCCL uses NVLink inside each and InfiniBand between them.
  • How NCCL does it (from its logs): all-gather and reduce-scatter run as rings (RING, no NVLS or CollNet), one per channel, with 4 channels per NIC of the NVL domain up to 32 (16 with NVL domains of 4, 32 with 8). Each ring crosses every NVL domain boundary through one NIC, and since every GPU is on every ring, each GPU sees the NVL domain's combined NIC bandwidth. Each channel takes one SM, so the compute slows less with NVL domains of 4 (1.18x) than with 8 (1.3x, as inside a 64-GPU NVL domain).

PyTorch nightly (2.16, CUDA 13) with its NCCL 2.32. Every timed run used NCCL_DEBUG=WARN: the hosts' default per-call logging distorts timing.

Bandwidth (coll_bw.py). All-gather, reduce-scatter and all-to-all over every GPU of the job, and send/recv from rank i to rank i + N/2 (so each pair spans two hosts), at 1 MB to 2 GB. Each size runs a few warm-up calls, then a timed loop on CUDA events; the slowest rank's time counts. Bus bandwidth follows nccl-tests: bytes x (N - 1) / N / time for the collectives, bytes / time for send/recv.

Overlap (kimi_k3_overlap_bench.py). For each pair of a compute kernel and a collective:

  1. Time each alone. All ranks adopt rank 0's times, so every rank sizes its loops identically and issues the same number of collectives (otherwise the ranks deadlock).
  2. Queue enough back-to-back collectives on a side stream to outlast about 200 ms of compute, then run the compute on the main stream, and time both.
  3. Compute slowdown = the compute's time per call while overlapped over its time alone.
  4. Collective slowdown: the collectives start with the compute and outlast it; after the compute ends they run alone at their solo rate. Subtracting the calls that fit in that tail gives the calls done during the overlap, and the overlap window divided by those calls' solo time is the slowdown.
  5. NCCL SMs: the thread blocks (one per channel, one SM each) of the collective's kernel, from a profiler trace.

The compute kernels are an MXFP8 and a bf16 GEMM at a KDA projection's shape (8,192 x 7,168 x 12,288) and a memory-bound elementwise kernel over 1 GiB operands (on the cluster, bf16 only: its image has no torchao). Within one host we also swept NCCL's channel count (NCCL_MAX_NCHANNELS = 32, 16, 8, 4).

One-way transfers (PP hops). The first half of the ranks only send, each to its partner in the second half, which only receives; every rank also computes, and each reports its own compute slowdown. Within one host the pair is 2 GPUs over NVLink; across hosts it is rank i on one host and rank i on the other, 4 pairs at once, so each transfer uses its own NIC.

B.7 Why Plain 1F1B Exposes Its Hops

The in-flight limit. After warmup, plain 1F1B lets stage s hold only P - s microbatches at a time: that is what bounds its activation memory. It is just enough work to keep the stage busy while a microbatch makes its round trip down the pipeline and back, if the trip were compute only. In the 1F1B chart of Section 7.1, the boxed gap on stage 0 shows what happens: after F5, stage 0 has F6 ready, but starting it would mean holding a fifth microbatch, more activation memory than 1F1B allows. It has to run B2 first, and B2 waits for its gradient's hop.

It is the extra microbatches, not the chunks. Interleaved 1F1B's warmup runs (v - 1) P + 2 (P - 1 - s) forwards on stage s, twice the P - 1 - s extra that keeps the pipeline busy. Swapping the two warmups in the simulation (four stages, forward 1, backward 2, hop 0.5) shows which one hides the hops:

Schedule Warmup forwards on stage s Hops added to the step per extra microbatch
Plain 1F1B P - 1 - s (standard) 1.5
Plain 1F1B 2 (P - 1 - s) 0
Interleaved (v - 1) P + (P - 1 - s) 3
Interleaved (v - 1) P + 2 (P - 1 - s) (PyTorch's) 0

The step without hops is the same in each pair: the doubled warmup only adds slack, and costs the activation memory of the extra microbatches.

Receiving early. A transfer between two GPUs needs both to take part: the receiver must give NCCL a buffer for the data ("post a receive") before it can move. We assume both schedules post each receive as soon as they know the data is coming. A receiver that posts it only when it needs the data makes every hop start late: PyTorch's plain 1F1B does that for activations, which adds about 0.1 hop per microbatch; its interleaved schedule posts early.
